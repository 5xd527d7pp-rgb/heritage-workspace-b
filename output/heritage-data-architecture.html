grill-me で決まった方針

誰が使うか

  • 編集は本人1人（複数端末から）
  • 成果（本文・Word）は他者が閲覧
  • 共同編集はしない

アプリの形

  • フル編集アプリとして仕上げる
  • 講座課題としてDB を使う
  • 複数計画を最初から対応

正本 (SSoT)

  • DB が正本
  • hybrid 版は DB → Git/Markdown の一方向
  • 双方向同期はやらない

  • 編集はログイン必須

何を・どこに保存するか

第7回講義の核心は「文字データとバイナリは分ける」こと。文化財計画ツールでも同じです。

DB（Neon Postgres）

表形式で整理整頓。複数端末から同じデータにアクセスするための正本。

  • ・計画メタ（表紙・公開設定）
  • ・章節・本文（Markdown）
  • ・要件・素材・紐付け
  • ・画像メタ（番号・出典・URL）

Blob（Vercel Blob）

写真・図の実体ファイル。DB に入れると重く、Git も向かない。

  • ・分布図・地図・現地写真
  • ・DB には blobUrl だけ
  • ・HTML の img は「住所」

Git / Markdown（hybrid）

後から追加するミラー。AI（Cursor）が本文に密着するためのエクスポート先。

  • ・DB → .md 一方向
  • ・双方向同期はしない
  • ・正本は常に DB

よくある誤解：「リストも写真も全部 DB に入れる？」

DB に入れる

  • リスト → 本文 Markdown の `-` 行
  • 画像の参照 → images テーブルの URL
  • 図表番号・出典 → images テーブルのメタ

DB に入れない

  • JPEG/PNG の実体 → Blob
  • 理由：重い・差分管理不可・Git 容量限界

本文 = Markdown、画像 = 参照

heritage-workspace-b — 第2章 第1節
# 2-1 地域の概要
本市域は...
- 文化財の種類：建造物、記念物

出典：○○市文化財台帳
sections.body（TEXT）

Markdown 文字列そのまま保存。リストは `-`、画像は `![](url)` で参照。

images テーブル（フルメタ）
kind: 写真 / 図 / 地図
number: 図1, 写真2（自動採番）
caption, source, blobUrl
Vercel Blob

fig-001.png の実体ファイル。DB には URL だけ。

なぜ Markdown？

AI に文章を書かせるなら Markdown が最も軽い（第7回講義）。JSON/SQL は AI に重い。将来 hybrid 版で Git にエクスポートするときも、.md ファイルにそのまま落とせる。

DB 構造 — plans を根に planId で紐付け

複数計画対応のため、plans テーブルが親。他のテーブルはすべて planId で紐付く（講義の candidates ↔ interviews と同じ構造）。

すべて planId で親に紐付く

現状の schema.ts（zod）がデータ契約の SSoT。この型を DB 行にも Markdown エクスポートにも使い回す。

公開とアクセス — 計画ごとに ON/OFF

編集（本人のみ）
  • ログイン必須（単一ユーザー/パスワード）
  • 本文・要件・素材・画像を編集
  • 会社・自宅・スマホから同じ DB
閲覧（他者）
  • 公開 ON の計画だけ見える
  • Word 出力・本文閲覧
  • 編集・削除は不可

hybrid 版への準備（今から効く布石）

DB版を作りながら hybrid を見据える3つの布石

1

ストレージ層をインターフェース化

storage.ts の「読む/書く/消す」を契約に。DB 実装と Git/ファイル実装を差し替え可能に。

2

schema.ts (zod) を唯一のデータ契約に

DB 行も JSON も Markdown も同じ型に直列化・復元。型が揺れない。

3

本文=Markdown / 画像=参照URL

DB の TEXT でも .md ファイルでも等価。後からエクスポータを足すだけ。
